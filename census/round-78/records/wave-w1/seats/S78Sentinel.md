# S78Sentinel — safety review of the W gate git-discovery pre-check (r78 C1 surface)
Bytes tested: tools/souji-pre-report-gate.sh at W ed22dc9c (blob 5795d655, sha256 b746bd9d…, lane HEAD bbd199da for that path), copied to scratch; fixtures built there. Lane and host untouched; no sudo, no tool installed.
Verdict: the 17 frozen rows are not re-derived here (counter seats own them). On my surface the new pre-check is not safe: it can be made to fork without bound, and two value spellings slip a FIFO past it.
HIGH-1 the include walk is a fork bomb, unbounded before any refusal (probe-fanout.sh).
  B=2 tree: gate = 1025 `git config` fork+execs, 10.0 s, rc=1; the SAME tree in `git rev-parse` = rc=128 "exceeded maximum include depth (10)" in 4 ms. B=4: 4^10 ≈ 1.4M nodes, still running at the 60 s cap (1552 done, rc=124). B=10 ≈ 1.1e10 nodes. Node paths differ by dirname spelling (x/../a, then x/../x/../a, …) so the exact-string seen-set never dedupes; `(( depth <= 10 ))` bounds depth only, never total work, and the 45 s timeout is per node. git aborts at the first depth overflow; the gate walks the whole tree first.
  Impact: a mandatory gate run on a hostile repo stalls for hours–years at 100% CPU, then refuses. Smallest fix: map git's depth error to the refusal and stop, or cap total nodes.
MEDIUM-1 a newline in an include value is truncated, hiding the real target (probe-newline-include.sh).
  `path = "nl\nfifo"` → scan prints two lines; `[[ $line == *' '* ]]` drops line 2, v="nl", .git/nl absent → PASS. git includes .git/nl\nfifo (FIFO), verified blocked (rc=124 at an 8 s cap). End-to-end: check-gitsource=PASS, check 1 blocked 45 s → `detail-tip: RECEIPT-GIT-TIMEOUT`, then check 4's rev-parse blocked under its 300 s timeout (still blocked at a 120 s outer cap). ≈45+300 s instead of an instant refusal. Fix: `git config -z` and split values on NUL.
MEDIUM-2 the refusal count mislabels non-refusal causes as non-regular files (probe-fanout.sh).
  B=2 tree: `find .git ! -type f` = 0, yet `RECEIPT-NONREGULAR-GITSOURCE: 1024 git configuration/ref source(s) are not regular files` (depth-cap hits); a `git config --file` rc=128 (bad config) is counted the same way. The class line is therefore forgeable — a hostile repo sets the count at will. Fix: separate classes (depth / unreadable) from the non-regular count.
MEDIUM-3 SIGTERM (S77Sentinel MEDIUM-3) still open, narrowed (probe-sigterm.sh).
  TERM to the gate during check 1: gate exits, `timeout -k 5 45 git rev-parse` and git survive, reparented to PID 1 (LEAK=2; 4 in a run overlapping a 300 s check-4 pair). No trap in the gate, no group kill. Before W the survivor was unbounded; now ≤45 s (check 1) / ≤300 s (check 4).
LOW-1 path-model divergence: git expands `%(prefix)` → /usr/… and `~user` → /root/…; the gate resolves both dir-relative and checks nothing (probe-expand.sh: gate PASS, git reads /usr/share/git-core/templates/description). Not exploitable here (root-owned), but a hole under any user-writable install prefix.
LOW-2 `gitsrc_seen` is a `|`-joined string with no escaping: a path containing `|` aliases a path never scanned (probe-seen-pipe.sh: `/x/a|/x/b` → SKIPPED). End-to-end needs the absolute lane path inside a filename (my build did not skip; the scan opened .git/./A|.git/./B).
LOW-3 `-f` admits every regular host file, /proc pseudo-files included (/proc/kmsg, /proc/self/mem are `-f` regular); here they read in ≤20 ms or EACCES, and the 45 s per-node timeout bounds one. A blocking *regular* target would cost 45 s × the number of include lines (no total budget).
PASS-1 (#2 expansion): values are never shell-expanded — `"$(touch …)"`, "`touch …`", "./*" pass through literally (EXPANDED absent, no globbing, nothing opened).
PASS-2 (#1 devices): FIFO blocks `git config` (rc=124, 5 s cap) but `-f` refuses it; unix socket, char device, /dev/stdin are `-f=no` → refused in 2–20 ms. 115 MB regular config = 938 ms, linear, under the 45 s bound.
PASS-3 (#4 D30): the new refusal lines print counts only — grep of stderr for the fixture path and for HEAD = 0 (probe-d30.sh). Pre-existing `detail-clean: %s "$status"` at :188 still echoes git-status paths (not new code).
