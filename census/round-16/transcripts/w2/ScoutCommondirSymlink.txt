218:## Answer
219:
220:**Yes — git follows a symlinked `$GIT_DIR/commondir` and reads the link target's content.** Existence is tested with `lstat` (the link itself counts, even dangling), then the file is opened by name, which the kernel follows:
221:
222:- `get_common_dir_noenv` — `setup.c:327-330` (master, identical block in released `v2.52.0`): `strbuf_addf(&path, "%s/commondir", gitdir)` → `file_exists` → `strbuf_read_file`, dying with `"failed to read %s"` on failure. https://raw.githubusercontent.com/git/git/master/setup.c, accessed 2026-10-20.
223:- `file_exists` = `lstat` — `dir.c:3204-3208`: `"int file_exists(const char *f) { struct stat sb; return lstat(f, &sb) == 0; }"`.
224:- `strbuf_read_file` = `open(path, O_RDONLY)` — `strbuf.c:782` — follows the link. A dangling link, a directory target, or a 0-byte file all hit `<= 0` and make git **die**; git does not treat them as "no commondir".
225:- Normalisation: only trailing `\n`/`\r` are stripped (`setup.c:331-334`); relative content joins `$GIT_DIR` (`setup.c:337-338`); the result is `realpath()`ed with die-on-error (`setup.c:339`, `abspath.c:318-325`). Docs confirm: `gitrepository-layout.adoc` — "If the specified path is relative, it is relative to $GIT_DIR."
