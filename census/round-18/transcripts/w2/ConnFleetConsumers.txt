# Finding
`run_repo_with_watchdog` (`5efb519:tools/souji-census.sh:1478-1501`) starts the worker with `set -m` and the timer with `setsid`. The timer kills that group only after `mkdir "$state_path"` (`:1492-1499`). `state_path` lives under `CENSUS_TMP`, and the only cleanup is `trap cleanup_census_tmp EXIT` (`:232-241`), which `rm -rf`s that directory.

`kill_mission` (`scripts/shokunin-watchdog.sh:253-286`) sends TERM, waits about 5 seconds, then KILL, all to the lane group recorded at launch (`:209-221`). The worker pgid and the timer session are not in that group.

Static trace, under ordinary fork inheritance (census never `setsid`s itself):

1. A landed report calls `kill_mission` (`:349-357`).
2. SIGTERM hits the census parent. The EXIT trap deletes `CENSUS_TMP`.
3. Worker and timer survive.
4. The timer only watches `kill -0 -- "-$pgid"` (`:1487-1492`). At the default 600s bound, `mkdir` fails and it exits without signaling.
5. The driver treats the lane group as gone and launches the next round (`:360-361`) while the repo worker is still alive. The 450s tick does not reap it.

This composes with the parent-EXIT hole in `SentinelWatchdogImpl.md` and `RevWatchdogDiff.md`. Those cover a parent-only signal. The outside driver that sends it is `kill_mission`. An EXIT-trap signal in the parent still loses on SIGKILL, and the current trap deletes the directory the timer needs. The timer is what survives the group kill, so the reap has to live there and has to run when `mkdir` fails.

# Proposed move
In the `setsid` watchdog at `tools/souji-census.sh:1482`, pass the census pid (`$$`). If `kill -0` of that pid fails, TERM then KILL the worker group and exit. At the deadline, if `mkdir "$state_path"` fails, still TERM then KILL the worker group. Leave the header, the `error` row, exit 0/2/3, and the live-parent timeout path unchanged. Keep the `setsid` dependency so the timer outlives the lane group.

# Risks
- Pid reuse can hide parent death for one poll. The deadline path still signals when `mkdir` fails.
- Do not use the timer's PPID. With `set +m`, util-linux 2.42.4 `setsid` execs in place. `--fork`, or a launch where `setsid` is already a group leader, reparents the timer while the parent is alive and a PPID check would kill a healthy run.
- If a substrate `setsid`s the census tool itself, `kill_mission` never signals it. The in-process timeout still applies. This move does not cover that case.
