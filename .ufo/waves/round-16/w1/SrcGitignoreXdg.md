## The quote

gitignore(5), § DESCRIPTION, lines 243–246 (verbatim, web rendering):

> Patterns which a user wants Git to
> ignore in all situations (e.g., backup or temporary files generated by
> the user’s editor of choice) generally go into a file specified by `core.excludesFile` in the user’s `~/.gitconfig`. Its default value is
> $XDG_CONFIG_HOME/git/ignore. If $XDG_CONFIG_HOME is either not set or
> empty, $HOME/.config/git/ignore is used instead.

Supporting anchors on the same page:

- line 199 (§ SYNOPSIS): `$XDG_CONFIG_HOME/git/ignore, $GIT_COMMON_DIR/info/exclude, .gitignore`
- lines 226–227: `core.excludesFile` is the **last** source in read order (highest → lowest:
  command line, `.gitignore`, `$GIT_COMMON_DIR/info/exclude`, `core.excludesFile`)
- lines 282–285: exclude sources outside the working tree (including `core.excludesFile`)
  are treated as specified at the working-tree root
- lines 328–330 (§ CONFIGURATION): `core.excludesFile` is optional and its patterns are
  "used in addition to those in `$GIT_COMMON_DIR/info/exclude`"

Literal spelling note: the page writes `$HOME/.config/git/ignore`, not a literal `~/.config`;
the fallback condition is "either not set or empty".

### What the quote grounds

- High confidence: the default value is `$XDG_CONFIG_HOME/git/ignore`; the fallback
  triggers when `$XDG_CONFIG_HOME` is "not set or empty"; the fallback is
  `$HOME/.config/git/ignore`. Code lines 884–889 match this exactly for `leaf=ignore`
  (`:937`), and the same documented shape exists for `core.attributesFile` /
  `leaf=attributes` (`:938`, gitattributes 293–296).
- High confidence on source rank *as documented*: `core.excludesFile` is the
  lowest-precedence exclude source (gitignore 226–227), and outside-worktree exclude
  sources anchor at the worktree root (282–285). [INFERENCE] Treating
  `-c core.excludesFile=<path>` as replacing that source's value rather than adding a new
  source rests on config-scope semantics from git(1)/git-config(1) (S036/S042), not on this
  page; the page's own wording ("used in addition to" `info/exclude`, lines 328–330) is
  consistent with a replacement of the same source.
- Not grounded: that the file exists, is read successfully, or that dirty counts are
  unchanged. This page is prose about path selection only.

## Calibration boundaries (quote does NOT cover these)

- **B1 set-but-empty `core.excludesFile`.** `val=$(git config --get "$key")` +
  `[ -n "$val" ]` (`:876-877`) sends an explicitly empty value into the XDG branch. The
  page defines the *default value* and the `$XDG_CONFIG_HOME` empty case, but says nothing
  about `core.excludesFile =` (empty value). Whether Git itself then uses the XDG default
  or loads no file is not decidable from these pages. If Git diverges, census would honor
  the user-global ignore where a plain `git status` would not (its own `-c` override makes
  the computed value authoritative for the census run). Q2 falsifier, not run here:
  tagged `dir.c` at v2.55.0 plus a `/var/tmp` fixture comparing
  `git -c core.excludesFile= status --porcelain` with unset-config status while an XDG
  ignore file matches an untracked file. Confidence: medium that this is a real divergence.
- **B2 missing default file.** `-f` failure → `/dev/null` (`:897-901`). The page states no
  missing-file rule; "no patterns loaded either way" is an inference, not a quote.
- **B3 relative `$XDG_CONFIG_HOME` / unset `$HOME`.** Code returns `/dev/null` (`:885-893`).
  The page is silent; the XDG Base Directory specification (not opened this round) is the
  usual authority. Do not attribute B3 to S043.
- **B4 symlinked ignore file.** `resolve_guarded` follows symlink hops (with protected
  checks and a hop cap) and `-f` accepts a regular target. The gitignore NOTES sentence
  "Git does not follow symbolic links when accessing a `.gitignore` file in the working
  tree" is scoped to working-tree `.gitignore` files, not `core.excludesFile`; the page
  neither authorizes nor forbids following a symlinked excludes file. Unclaimed.
- **B5 attributes `/dev/null`.** The gitattributes page contains no `/dev/null` sentence,
  so using `/dev/null` as a neutral `core.attributesFile` is implementation policy plus the
  inference that an empty file yields no attributes. Unclaimed by S044.
