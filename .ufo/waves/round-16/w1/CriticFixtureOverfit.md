## Counterexamples the r16 oracle cannot see

1. **Unaffected-row survival is claimed but never tested.** The comments on 03, 07 and 14 justify the change with "no other row is suppressed" and "other rows survive". But `soft_repo` and `single_positive` (fixture 1010-1050) run each repo alone (`--root <repo> --include-root`), and the only mixed fleet with a bad repo (17) is a protected reach. A tool that prints the soft row and then drops or zeroes every later repo, with exit 0, passes 03, 07 and 14 as written. This is the exact Q22 property the change exists for.
2. **Soft-before-protected precedence is unconstrained, and cbf688a gets it wrong.** cbf688a `scan_config_file` (cbf688a:579-617) returns soft at the *first* soft record: `expand_config_path` sends `~user`/`%(prefix)` to `cfg_soft` (540-547, 611-613), and cycle, depth or nonregular checks also return early. Later records are never evaluated. Take a config with `include.path = ~root/x` followed by `include.path = <store>/secret.gitconfig`. It yields an `error` row and exit 0, where the contract says a protected reach must exit 2 with `path-protected`. The same happens to a store include placed after a cycle edge. No store bytes are read (no git runs in that repo), so this is a loss of the refusal shape, not an access breach. Still, it contradicts the fixture docstring ("every verified namespace refusal still refuse") and C1 ("only a protected-namespace reach keeps whole-run exit 2"). Each fixture soft case is pure-soft, so the oracle cannot detect this. [INFERENCE from source; not executed.]
3. **`~user` targets are degraded whatever they point at.** `~<self>/.omp/agent/x` is a protected reach, but cbf688a never resolves it (getent passwd is already used in `passwd_home`). The 03 oracle pins "~user → degrade", which encodes the implementation's simplification. I classify this as a tradeoff for the judge, not a defect, because nothing is read.
