## Findings

- **MEDIUM** — the git(1) page has TWO different `GIT_NO_REPLACE_OBJECTS` sentences and the S301/S298 chain cites only offsets, not which. Anyone re-verifying `git-environment.txt` byte 10850 (line 485, the option-description occurrence: "This is equivalent to exporting the GIT_NO_REPLACE_OBJECTS environment variable…") with the intent of the env-var-entry quote would silently pass on the WRONG sentence. The entry actually cited by quotes.tsv:12-13 is the ENVIRONMENT VARIABLES one at byte 46311 (line 1413), which is correct, but the prose that says "byte offset 46334" without naming the section is one digit away from the wrong entry. Everything else in the chain was byte-exact, so this was caught here rather than corrupting the corpus. Recommend the L1 prefer the r66 quotes.tsv `section` cell (`ENVIRONMENT VARIABLES`) when citing the entry, not the bare offset. Evidence: my raw byte probes 101967/220857 on git.html and 10850/46311 on the r66 capture.
- **LOW** — `GIT_NO_REPLACE_OBJECTS` in the S298-cited git(1) entry is described as "Setting **and exporting** this environment variable tells Git to ignore replacement refs…"; the option-description sentence on the same page says "**exporting** … with any value." The knowledge entry and registry row both paraphrase the trimmer `GIT_NO_REPLACE_OBJECTS=1 is the documented way` — accurate but the exported-value nuance ("any value", not just =1) is dropped; harmless here because the writer pins `=1`, but a future claim should keep the "any value" wording if it ever generalizes. Evidence: the raw entry text at 220857 (git.html) and the r66 capture line 1413-1415.
- **LOW** — the knowledge entry (`knowledge-replace-ref-receipt-writer.md`) says the two sentences "match byte-for-byte in the recipe-stripped page text" — correct for the 96d141fd text. In the RAW HTML neither sentence is a contiguous byte run (internal newline in (a); `<span><code>` wrapping in (b)), so no report should repeat "byte-for-byte" without the "recipe-stripped" qualifier. Both seats' wording already carries it; this note exists so a summarizer doesn't drop it.
- No **HIGH** findings.
