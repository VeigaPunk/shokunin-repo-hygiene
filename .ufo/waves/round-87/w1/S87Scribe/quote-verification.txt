## 7. FINDING F2 — the COMMITTED tip bytes mis-parse a rename's second NUL field (HIGH, C2 wording)

The claim C2's stated wording says (preregistration.txt:78-79, verbatim):

    "(the -z form's second NUL field of a rename is skipped; the rename record itself already reaches the key)"

and the frozen stated limit at preregistration.txt:111-112 says:

    "the -z arm skips a rename's second NUL field, so a renamed destination is named only through its rename record"

The COMMITTED tool at refs/heads/master (6e502c5c, `tools/souji-record-agreement.py` blob 4244ac26, sha256
0ad9e3bf…) skips that field by a CONTENT test, at its line 476:

    if len(rec) < 4 or rec[2:3] != " ":
        continue
    path = rec[3:].replace("\n", "\\n") ...

`rec[2:3] != " "` asks "does the third byte look like the separator after a status pair?". For a rename's SECOND
field the third byte is just the third byte of the OLD path. When the old path's third character is a space, the
test passes and the old path is mis-read as a status record.

Reproducer (hermetic fixture, no lane byte read or written; `git -C "$D" rev-parse --show-toplevel` asserted
equal to $D before the first commit; D under the seat's scratch root, not /tmp):

    $ git -C "$D" init -q
    $ printf 'hello\n' > "$D/my file.txt"; git -C "$D" add -A; git -C "$D" commit -q -m seed
    $ git -C "$D" mv "my file.txt" "new.txt"
    $ git -C "$D" status --porcelain -z | od -c
    0000000   R           n   e   w   .   t   x   t  \0   m   y       f   i
    0000020   l   e   .   t   x   t  \0

    $ python3 -B <tip tool bytes> --root "$D" --rev "$(git -C "$D" rev-parse HEAD)" | grep '^MISMATCH\tK4'
    MISMATCH	K4	new.txt	uncommitted-path	R
    MISMATCH	K4	file.txt	uncommitted-path	my

The second row is SPURIOUS: the record `file.txt` does not exist in the tree, and its detail `my` is the first two
bytes of the old path read as a status pair. The old path is `my file.txt`; the record names `file.txt` (the tail
after three bytes) and the detail names `my`.

Control (same fixture shape, old path with no space at byte 2 — `oldname.txt`): the tip tool emits ONE K4 row
(`new.txt`), so the defect is specific to an old path whose third byte is a space, not to renames in general.

Compare the lane-base tool bytes (the C2 before-arm control, cf875367…): on the same fixture it emits ONE row,
`MISMATCH	K4	"my file.txt" -> new.txt	uncommitted-path	R` — the line form's git-quoted spelling, which is the
defect r87 set out to fix (C2 §2e). So on this fixture the committed tip is not better than the base: it trades one
wrong spelling for a different wrong spelling PLUS a spurious extra row.

The WORKTREE bytes (S87ExecC2's repair, sha256 c2b0784e…) skip the field by STATUS LETTER instead of by content,
and emit ONE correct row on the same fixture:

    MISMATCH	K4	new.txt	uncommitted-path	R

This seat did not write that repair; it is S87ExecC2's, already in the lane worktree. It is recorded here because the
L1 must decide what the C2 after arm is filed against (the committed tip bytes mis-parse renames; the worktree
bytes do not) and because the claim's STATED WORDING about skipping the rename's second field is TRUE of the
worktree bytes and FALSE of the committed tip bytes for an old path whose third byte is a space.

Scope of the finding: it is a class of the lane's own instrument's reach, measured on the lane's own committed
bytes with a synthetic fixture; it is not a claim falsifier (C2's stated wording is about the tool's behaviour, and
the tool's behaviour is what the repair changes) — but the C2 after receipt MUST be re-filed against the committed
repair bytes, and the Gate's "the -z arm skips a rename's second NUL field" sentence must name the skip's RULE

## 9. FINDING F9 (MEDIUM, the L1's COMMITTED bytes) — the same arm escapes a raw control byte, so the record can be
##    split by a line-oriented consumer

The FORGED-detail arm's escape at line 305 covers only `\n`, `\t`, `\r`. A VT (0x0b) in a TRACKED path's name
therefore lands RAW in the record. Measured on the committed bytes with a tracked `vt<VT>name.txt` forged under the
index stat cache, the detail's bytes carry the raw 0x0b:

    0000240   t  \v   n   a   m   e   .   t   x   t   )   ;       t   h   e

A raw 0x0b is a `str.splitlines()` separator, so a consumer that splits the record on line boundaries reads this
row as two lines — the same defect class Q159 names ("joining those to spaces both splits a line-oriented record
and loses the name a reader must act on"), reached through the byte the escape does not cover. The STATUS arm does
not have it: the same name in the STATUS arm reads `vt\x0bname.txt` (escaped, one record). So the two arms of ONE
row set still spell one path two ways, which is what A3's "one path has one spelling in both arms" names as closed.
