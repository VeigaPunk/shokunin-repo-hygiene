## The predicate under attack — tools/souji-record-agreement.py k1() (lines ~146-186)

The key logic: on each r22/round-22-scoped physical line, `bound` = the last 40-hex
token *before* the tuple on that same line; if `bound == rev` the tuple must equal the
receipt's first `assertions=` match; if `bound != rev` the tuple is flagged only when it
*equals* the receipt value (`rev-disagree`); a tuple with no token or a token `!= rev`
and a value `!= receipt` is **silently ignored** (not counted, not flagged). `seen == 0`
→ `occurrence-absent`.

## Findings

### F1 (HIGH) — token-moved + wrong value is silently ignored; K1 can green while the record's after-value is false
Root cause: `rev-disagree` is only emitted when the tuple *equals* the receipt value;
`value-disagree` is only checked on tuples bound to `rev`. A tuple that is neither is
dropped entirely (`occurrences` drops 17→16 — the only trace). Reproduction: rev `da71632`
in the matrix — SCORECARD quotes `mismatches=9` for the r22 after-state and K1 reports
`mismatches=0`. Prereg K1 says "the r22 C1 after 4-tuple quoted in SCORECARD.md must
equal the counts line" — a quoted, wrong after-tuple violates that literally.
**Fix**: flag every in-scope tuple that is either (a) bound to `rev` and unequal
(value-disagree), (b) bound to another rev and equal to the receipt value (rev-disagree,
today's branch), **or (c) bound to `""`/other rev AND unequal — currently dropped**;
the only legally free tuple is one bound to a different named revision that does not
equal the receipt value *and* is not the after-claim shape — the lane's own before-tuple
is allowed only because it is bound to a named revision; an unbound tuple should always
be `rev-disagree`. Must fix or disclose.

### F2 (HIGH) — the binding is not anchored to the C1 calibration row; any line anywhere satisfies it
`K1_RECORDS = ("SCORECARD.md",)` and `seen` counts *any* bound tuple on *any* r22-scoped
line. Reproduction: rev `ce69f08` (old tool) and `89c4a22` (466f539 tool) — the
calibration row's after-value is wrong in both the verdict and counting-command cells,
and a single decoy line in prose keeps M=0. Prereg names the tuple "the r22 C1 after
4-tuple", i.e. the calibration row's quote; the predicate does not know which row it is.
**Fix**: require ≥1 bound occurrence in the axes-table calibration row (e.g. line in the
`| calibration |` row shape), or disclose that K1 verifies only "some r22 line".

### F3 (MEDIUM) — `rev=` is never resolved; a receipt bound to a nonexistent object stays green
`counts_of` returns the receipt's self-declared `rev=`; the code checks equality of
tokens but never `cat-file -e`. Reproduction: rev `fb4f8ee` — receipt and record agree
on `0000…0` (`git cat-file -t` → rc=128, no such object), M=0. Within the frozen letter
(prereg requires token equality + receipt existence at `--rev`, not rev resolution), so
this is a contract gap — but "the receipt binds the r22 after-state" is vacuous when the
named revision is fabricable. **Fix**: `git cat-file -e <rev>` on the receipt's rev
(existence only — never "is it the commit containing the receipt", which is impossible
by construction and correctly not checked).

### F4 (MEDIUM) — the receipt's authoritative counts line is the first `assertions=` match *anywhere*, not the `--- stdout ---` block
`counts_of` is `COUNTS_RE.search(text)` over the whole file, `REV_LINE_RE.search`
likewise takes the first `^rev=`. Reproduction: rev `df861fe` — a `# note` line carrying
the record's expected tuple precedes a stdout block that disagrees; K1 takes the note.
**Fix**: parse the counts line only inside/after the `--- stdout ---` marker (and the
`rev=`/`tool_sha256` headers only before it).

### F5 (LOW) — K1 ignores `tool_sha256`; a receipt C2's verifier calls forged still counts as bound
rev `f1bf75d`: stale r22 digest → K1 M=0 while `souji-receipt-run.py verify` exits 2
`RECEIPT-TOOL-DIGEST-MISMATCH`. Cross-instrument disagreement on the same receipt;
receipt integrity is C2's frozen claim, so the correct disposition is **disclose** as a
named limit ("K1 binds value+rev text; receipt integrity is verify's job").
