## T1. Does a `superseded by` line placed *above* the stale tuple satisfy the rule?

**Yes — one line above, inside the same paragraph, satisfies it.** The word "later"
is never enforced.

Code path — `tools/souji-record-agreement.py:235-244`:

```python
for occ in stale:
    later = any(
        K2_CORRECTION_MARKER in " ".join(lines[k:min(k + 6, len(lines))])
        and occ in " ".join(lines[k:min(k + 6, len(lines))])
        for k in range(start_line, len(lines))
    )
```

`start_line` is the stale *paragraph's* first physical line (`paragraphs()`, :67-86,
returns `offset + start`). The predicate is therefore not "a later line" but:

> there exists a 6-physical-line window, whose start index is at or after the stale
> paragraph's first line, that contains both the marker string and the occurrence
> string.

Consequences, all measured. Filed LOG bytes with the correction block removed
(`git show 1208bfb:LOG.md`), so nothing masks the result:

| mutation | rc | K2 rows |
|---|---|---|
| `R0` filed bytes, no correction block | 1 | 3 × `uncorrected` (tuple, `1 present`, `1 refused`) |
| `R1` marker line **1 line above** the tuple, same paragraph | 1 | tuple row **gone**; only the two tallies remain |
| `R2` marker as its **own paragraph** above (blank line between) | 1 | tuple row still present |
| `R3` marker **6 lines above**, same paragraph | 1 | tuple row still present |
| `R4` genuinely later correction paragraph appended at file end | 1 | tuple row gone |

`R1` output (verbatim):

```
MISMATCH	K2	LOG.md:1496	uncorrected	'1 present' has no later 'superseded by' line
MISMATCH	K2	LOG.md:1496	uncorrected	'1 refused' has no later 'superseded by' line
keys=4 records=4 occurrences=17 mismatches=2
```

So the effective rule is `|marker_line - occurrence_line| <= 5` with the window start
gated at the paragraph start. A marker *above* by <=5 lines passes; a marker *below*
by more than 5 lines fails. `R4` passes only because it re-quotes the tuple inside the
correction paragraph, giving a window anchored far below.

The false-negative direction is live on the real file. Tip LOG, item 1's marker word
replaced by an unrelated word while the correction sits ~45 lines below the filed tuple:

```
T2-tip-item1-marker-word-removed
MISMATCH	K2	LOG.md:1478	uncorrected	'assertions=56 resolved=53 skipped=33 mismatches=3' has no later 'superseded by' line
keys=4 records=4 occurrences=17 mismatches=1
```

and a marker moved ~60 lines below the tuple, in a later section (`G`), likewise
reports `uncorrected`. A *genuinely later* correction outside the 5-line radius is
rejected; an *earlier* one inside it is accepted.

## T2. Does deleting one of the three filed scalars still fail?

**Plain deletion fails correctly; deletion plus relocation passes.**

Code path — `:245-249`:

```python
section_text = " ".join(lines[body_start:end])
for expected in K2_FILED:
    if expected not in section_text:
        self.bad("K2", K2_RECORD, "filed-occurrence-missing", …)
```

This is a **whole-section substring test**, not a location test. It answers "does the
string still exist anywhere in the section", not "are the filed bytes intact".

Measured:

| mutation | rc | K2 rows |
|---|---|---|
| `B` delete `1 present` from the filed tally line | 1 | `filed-occurrence-missing '1 present' is gone` |
| `F` delete the filed 4-tuple from the section (correction block still quotes it) | 1 | `filed-occurrence-missing 'assertions=56 …' is gone` |

## T3. Does a stale scalar quoted inside the correction block itself count as covered?

**Yes, and the tip's green depends on exactly that.** The correction block is *outside*
the scanned section (`end` stops at the first `^=====` after the body, `:211-220`), but
`later` searches `range(start_line, len(lines))` over the whole file. A stale scalar
re-quoted in the correction block is therefore both (i) the thing that grants coverage
and (ii) never itself parsed.

Window probe against the real tip (`read_rows`-style walk of the same predicate):

```
PARA start_line=1478
  occ='assertions=56 resolved=53 skipped=33 mismatches=3' stale=True covered_windows=[1528, 1529]
PARA start_line=1495
  occ='1 present'  stale=True covered_windows=[1532, 1533, 1536, 1537]
  occ='1 refused'  stale=True covered_windows=[1532, 1533, 1536, 1537]
```

The only covering window for the 4-tuple is the correction block's own re-quote at
LOG.md:1529 plus the marker at LOG.md:1533. Nothing in the filed paragraph covers it.

Because the correction block is outside `paragraphs(lines[body_start:end])`, its
numbers are never compared to any receipt. Measured:

| mutation on tip LOG | rc | verdict |
|---|---|---|
| `C3` correction states `assertions=99 resolved=98 skipped=1 mismatches=0` | **0** | wrong replacement accepted |
| `C2` correction states `superseded by 9 present and 7 refused` | **0** | wrong replacement accepted |
| `C1` correction keeps the stale quote but the marker says only `superseded by the -final receipt` (no correct value anywhere) | **0** | marker word with no corrected number accepted |
| `T1` correction states **only** the correct `assertions=55 resolved=52 …`, drops the stale re-quote | **1** | correct correction **rejected** |

`T1` verbatim:

```
MISMATCH	K2	LOG.md:1478	uncorrected	'assertions=56 resolved=53 skipped=33 mismatches=3' has no later 'superseded by' line
keys=4 records=4 occurrences=17 mismatches=1
```

This is the sharpest inversion: K2 rewards re-printing the stale number and punishes a
correction that states the correct one without repeating the wrong one. The pass at the
tip is a property of prose style, not of correctness.

## Smallest safe correction

1. **Pin the filed bytes instead of substring-testing them.** Commit a receipt holding
   `sha256` of the r22 section body (`lines[body_start:end]`) as filed at `1208bfb`, and
   make K2 require that the same slice at `--rev` is byte-identical. That kills T1, T2
   (`B2`, `D1`) and the unpinned deletions (`H`, `I`) in one predicate and removes the
   hard-coded `K2_FILED` tuple as a source of drift.
2. **Restrict the marker search to lines strictly after `end`** and require the marker
   line to carry the corrected value taken from the receipt (compare
   `COUNTS_RE`/`TALLY_RE` on that line to `want_counts`/`want_tally`). That kills T1's
   above-marker acceptance, T3's `C1`/`C2`/`C3`, and turns `T1`'s correct-correction
   rejection into an acceptance.
3. **Fix the record, not the key:** correct `LOG.md:1576` to `mismatches=6`; replace
   `agreement-after.txt` with `agreement-after.tsv` at `LOG.md:1578` and
   `SCORECARD.md:21`, and either re-run the after arm at the tip that the row means or
   state the landing-tip value as `1`. As written the row cites a receipt that records
   the opposite of the claim.
4. Add fixture cases for: marker one line above the occurrence, marker six lines below,
   relocated occurrence, wrong replacement value, correct-correction-without-quote.
   Until then the `control=FALSE-GREEN-REJECTED` verdict does not cover K2's own
   acceptance boundary.

If (1)-(3) are not done before the round closes, C1's K2 line must be reported as
`unverified` rather than `mismatches=0`, per the prereg's kill rule.
